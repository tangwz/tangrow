# 原生中文输入法验收

本轮使用 macOS、Obsidian 1.15.0 和微信输入法，在独立临时库中验收写作流程。临时库与用户的笔记、目录和未提交草稿分开；原库不创建测试笔记，也不执行迁移。

## 当前证据与边界

2026-11-09 已记录到物理键盘通过微信输入法组字并提交中文，随后通过界面保存为临时库中的草稿笔记。记录中的 `keydown`、`compositionstart`、`compositionupdate` 和正文 `input` 为可信事件；候选提交对应的 `compositionend.isTrusted` 为假。本实现不以该标志拒绝组字结束事件，也不据此推断事件由哪一层转换。

自动按键与窗口快照曾出现焦点、目标窗口不一致；宿主输入框中的拉丁文本、粘贴中文和模拟事件均不作为完整原生中文验收通过的证据。下表仍区分已观测结果与尚未完成的场景。

后续只读检查确认：临时库中的独立 Tangrow 窗口与全局 `getMostRecentLeaf()` 返回的 Markdown 叶片属于不同 document；向该接口传入来源叶片的 `getContainer()` 后，返回的叶片属于来源窗口。这个独立窗口当时只有 Tangrow 面板，因此限定窗口后的目标是面板本身。该记录验证了窗口归属问题，不能替代慢速保存期间的原生交互。

后续验收使用自动按键驱动微信输入法，在临时库的两个真实 Obsidian 窗口观察标题双向同步、关闭组字窗口后恢复编辑，以及标题和正文的重载恢复。自动按键与人工物理按键分别记录，不将模拟宿主事件作为原生输入法证据。

## 关闭窗口时的未提交候选

在修复前的独立窗口中，微信输入法组字 `ni` 后立即关闭窗口：记录依次出现 `compositionstart`、`compositionupdate`、`insertCompositionText` 输入和失焦，但未观察到 `compositionend`。旧代码在输入事件和视图清理时发布控件当前值，导致未选择的拼音进入共享草稿。

现在组字中的控件值保留在本地输入框，不发布到共享草稿或自动保存；`compositionend` 后才发布完成的值。窗口或插件在组字未结束时关闭，将丢弃未确认的候选，保留组字前已提交内容及其他字段，并释放编辑锁。正常选定中文、明确提交的字母和未组字输入仍按原流程保存。

修复后的构建已在独立临时库的真实 Obsidian 窗口复验，使用自动按键操作微信输入法。分别在正文和标题中开始输入 `ni`，确认候选显示且保存按钮被禁用；等待自动保存后，插件数据仍保留组字前的值。关闭正在组字的独立窗口后，主窗口保留已提交内容、不包含新增候选，并恢复可编辑。随后在正文和标题分别提交中文候选，确认自动保存的数据包含选定文字，重载后两者均恢复。此前测试样本中已经存在的拼音保留不变，不视为本轮新输入。

写作暂存区的标题和正文在已提交的输入变化后约 350 毫秒自动写入插件数据；“另存为草稿”会显式创建 Markdown 笔记。尚在输入法候选状态的内容不计为已提交，也不会自动保存。

## 本轮代码修复

写作按钮显式传入来源叶片和正文控件。保存逻辑从该控件取得实际 document，并限定在来源窗口中查找 Markdown 文件视图；不再从全局最近叶片推断发起窗口。没有来源、来源窗口没有文件视图或目标被固定时，后台保存，不创建或替换面板。

慢速写入完成后，只有草稿版本、来源叶片、窗口、编辑控件、目标视图、笔记和焦点上下文均有效时，才在绑定的文件视图中打开已保存笔记。等待期间离开窗口、转移到其他控件或开始新的组字，会撤销这次导航资格；即使之后返回同一窗口和控件，也不会重新授权导航。较新的组字租约即使尚未改变草稿版本，也会阻止自动导航。正文、标题的清理仍由共享版本校验决定，完成回调不强制聚焦旧文本框。

导航上下文不可用不会把已成功的文件写入误报为失败。观察焦点和组字的临时监听器在写入成功、失败或上下文失效后释放。打开文件失败仍保留已保存结果，重试不重复创建同一草稿。

`tests/writing-origin.test.ts` 覆盖来源与全局最近叶片分属两个窗口、正常同窗口保存、离开后返回、暂时切换控件、新组字、新稿、缺少来源或文件目标、固定目标、窗口关闭、来源控件替换、目标笔记切换、写入和打开失败。它验证保存快照只写入一次、原有笔记不被修改、较新的草稿保留，以及所有最近叶片查询均限定在来源窗口。

这些回归使用模拟宿主，不能替代上表的原生输入法交互。

### 确认后紧接操作

- macOS 与 Windows 分别用系统中文输入法键选、鼠标选词，以及不改变文字的 Shift／Ctrl+Space 确认。立即从标题按 Tab 转正文、点保存、用保存快捷键、关闭速记小窗；重开后对照文字，并确认每次显式保存只产生一份笔记。
- 对照组：尚在候选状态时切面板、切应用或关闭小窗。即使先收到组字结束再失焦，也不能把未确认拼音写回普通草稿。验收只覆盖中文和英文输入；韩文、日文输入法不在目标用户范围内，不做真机验收。
- iOS：组字到一半点输入框外，记录 `compositionend`、`input`（`insertFromComposition`）与 `blur` 的先后，确认未选的拼音不进入草稿；在候选栏选词且不离开输入框时，确认选中的词保存。试用到期时的只读抢救是独立规则。
- 如果某种输入法只发出相同的组字结束与失焦序列，没有最终插入或确认键释放信号，应记录平台、输入法及事件顺序，不把短暂的延时本身当成确认依据。

### 组字期间失焦后回到同一控件

在 macOS 和 Windows 的临时库中，先输入一段已提交正文，再开始组字。分别在速记和写作暂存中操作，记录输入法、候选框是否仍在、操作顺序，以及控件收到的 `blur`、`focus`、`compositionend`、`input`（含 `inputType`）和确认键事件。

| 场景 | 验收条件 |
| --- | --- |
| 短暂失焦后回到原控件，同一轮组字仍在进行，此时选定候选 | 最终选中的词出现在共享草稿中，重载后可见。标出重新聚焦后的明确选词动作及对应事件。 |
| macOS 控件已收到组字结束事件，失焦撤回拼音后又回到原控件 | 一分钟内回来时提示重新组字一次；隔得更久再回来不提示。输入法作为普通文本送达的空格、数字或鼠标选中的汉字，原样进入共享草稿。重新组字后可用键盘选词。 |
| 失焦时已放弃候选，回到原控件后没有选词，仅收到上一轮迟到的 `compositionend` | 共享草稿与重载后的内容均保留组字前的正文，待选拼音未写入。 |

2026-11-22 在 Obsidian 1.15.1 的独立临时库中，Apple 简体拼音遇到控件连续失焦、聚焦时，实际顺序为 `compositionend → blur → focus`。旧候选栏此时仍可能可见。空格与编号键均产生普通 `insertText`，双击候选则产生包含汉字的 `insertText`。真实鼠标点到其他控件再返回时，候选栏已收起。微信输入法 3.0.2 也会在失焦时收起候选栏。

加入提示后，在速记正文和写作暂存正文分别复验了四种操作。返回控件只出现一次提示。空格和数字 `1` 原样保留，随后重新输入 `ni` 并按空格选出「你」，两段输入均在重载后保留。双击旧候选栏选中的「你」也能恢复。切窗放弃候选再返回时，重载后的草稿保留原文。八个样本的控件值、共享草稿、磁盘值与重载值一致。

Windows 原生事件顺序、同一轮原生组字跨越失焦后继续键选，以及重新聚焦后才收到旧的组字结束事件，仍待真机核对。验收时记录按键、最终插入和结束事件的先后，并检查重载后的草稿。

继续原生验收时，应在临时库分别检查同窗口文件视图、跨窗口文件视图和只有写作面板的独立窗口。在受控慢速写入期间离开后返回、切换后返回原控件，并通过微信输入法开始和取消候选；确认已有保存结果可找到、新稿保留、工作位置不被跳转、重载后草稿状态一致。需要物理输入的场景仍以原生事件及落盘结果共同验收。
