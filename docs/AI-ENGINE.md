# Tangrow 整理引擎设计

状态：设计提案，尚未实现。更新于 2026-11-26。

本文说明 Tangrow 如何在插件内部实现 AI 整理能力：每日回顾、卡片提炼、PARA 归位、卡片连接和主题百科（llm-wiki）；以及它和现有 Claudian 工作流、即时建议的关系。当前已实现的 AI 边界见 [设计边界](DESIGN.md#ai-功能的边界)，内容角色、关系和写入恢复约定见 [统一设计方案](ZETTELKASTEN.md)，术语见 [领域语言](../CONTEXT.md)。第 13 节的已定决策已同步进统一设计方案和领域语言；除此之外，本文与上述三份文档冲突时，在本提案被接受并更新它们之前，以它们为准。

## 1. 结论

Tangrow 定位为 AI 时代开箱即用的 Obsidian 个人工作台，由 PARA 和卡片笔记驱动（见 [产品定位](POSITIONING.md)）。整理引擎负责让核心闭环中的整理、提炼、连接、回顾四环由 AI 驱动；AI 承担整理劳动，判断权留给用户。为此：

- **自研整理引擎**。核心 AI 能力在 Tangrow 内完成，不要求用户另装插件；桌面端和移动端都可用；结果以 Tangrow 自己的变更清单呈现，由用户逐项确认。
- **不自研通用代理**。不实现任意文件读写、shell、开放式多轮工具调用。整理任务的边界都很清楚，用「选择上下文 → 结构化生成 → 确认 → 受控写入」的流水线就能完成。
- **Claudian 降为可选后端**，用于开放式对话和尚未迁移的工作流。已有的库级技能导出（`.claude/skills/tangrow-*`）保留。

当前做法与新做法的差异：

| 问题 | 当前（Claudian 工作流） | 整理引擎 |
| --- | --- | --- |
| 开箱即用 | 需要另装 Claudian、配置环境、选中对话 | 设置里填一次 API 密钥即可 |
| 平台 | 仅桌面端 | 桌面端和移动端 |
| 写入约束 | 只写在提示里，Tangrow 无法强制 | 写操作白名单由代码强制（第 5 节） |
| 确认方式 | 在聊天框里打字回复 | 可勾选、可编辑、带差异预览的变更清单 |
| 失败恢复 | 取决于代理 | 复用提炼凭据协议，重试不重新调用模型 |
| 接口稳定性 | 依赖实验性的插件 API v1 | 只依赖模型服务商的公开 API |

## 2. 目标与非目标

**目标**

1. 首批五项整理任务：每日回顾、卡片提炼、PARA 归位、卡片连接、主题百科编译。
2. 每次运行在发送前说明「会读哪些笔记、大约多少 token」，写入前列出「会改哪些文件、改什么」。
3. 所有写入都可预览、可部分接受、可恢复，不移动、不重命名、不删除已有内容。
4. 模型服务商可替换：Anthropic 起步，再支持 OpenAI 兼容接口（含自建或本地服务）。
5. 移动端可以完成每日回顾和卡片提炼。

**非目标**

- 通用聊天助手、任意指令执行、自动操作外部服务。
- 未经确认的后台写入。后台任务只生成提案，不落盘。
- 用 AI 判断卡片成熟度（`tangrow_stage` 仍由用户选择）或宣称观点已被证实。
- 向量数据库或嵌入检索。首期只用现有索引、链接关系和关键词；以后如有需要，作为上下文选择的一个可选来源接入。
- Tangrow 代付模型费用。用户使用自己的密钥（BYOK）。

## 3. 概念

以下是引擎内部的术语。确定后补进 `CONTEXT.md`。

| 术语 | 含义 | 不要混用 |
| --- | --- | --- |
| 整理任务（Task） | 一种可运行的整理能力，例如「卡片提炼」。由任务定义描述输入、输出和允许的写操作 | 不是 Markdown 里的复选框任务；界面上称「整理」或具体任务名 |
| 运行（Run） | 某个整理任务的一次执行，包括所选上下文、模型请求和返回的提案 | 一次运行不等于一次写入 |
| 提案（Proposal） | 运行产出的一组建议，每条附理由和依据的来源 | 不是已经发生的修改 |
| 变更集（Change Set） | 用户从提案中接受的、已固定内容的写操作列表 | 确认后不再随模型输出变化 |
| 变更项（Change） | 变更集中的一条写操作，类型必须在白名单内 | — |
| 托管区块（Managed Block） | 由 Tangrow 维护、带起止标记的一段正文，只用于主题百科页 | 区块外的正文始终属于用户 |

## 4. 架构

```mermaid
flowchart LR
  T[触发：按钮/今天页/命令/定时准备] --> C[上下文选择]
  C -->|预算与发送预览| M[模型适配层]
  M --> V[结果校验]
  V --> P[提案确认界面]
  P -->|用户接受并可编辑| S[变更集与恢复凭据]
  S --> W[写入执行器]
  W --> I[知识索引增量更新（E0 新建）]
  V -.->|校验失败| P
```

| 模块 | 建议文件 | 职责 |
| --- | --- | --- |
| 任务注册表 | `src/engine/tasks/*.ts` | 每个任务一个文件：上下文选择规则、提示词、输出 schema、把输出映射为变更项 |
| 上下文选择 | `src/engine/context.ts` | 基于知识索引、元数据缓存和设置选择笔记，按预算裁剪，生成发送预览。现有 `src/knowledge-index.ts` 只有纯解析函数，可查询的 `KnowledgeIndex`（链接邻近、共同来源、关键词）需在 E0 新建 |
| 模型适配层 | `src/engine/providers/*.ts` | 统一的 `generate()` 接口；服务商差异、重试、取消、用量统计 |
| 结果校验 | `src/engine/validate.ts` | JSON schema 校验；修改类变更项的目标、以及正文和属性中的链接，必须指向上下文中真实存在的文件，或指向同一提案中某个 `create-note` 将新建的路径（该项记为依赖这条新建）；`create-note` 的路径必须落在任务允许的目录内且当前不存在；丢弃越权的变更项 |
| 提案界面 | `src/engine/review-view.ts` | 侧栏或模态中的变更清单，支持勾选、编辑、预览差异 |
| 写入执行器 | `src/engine/apply.ts` | 只执行白名单写操作；修订核对；恢复凭据；与持久化协调器串行 |
| 运行记录 | 插件数据中独立的版本化记录 | 进行中的运行、待确认提案、变更集凭据、主题百科编译状态 |

任务定义的形状：

```ts
interface TaskSpec<Output> {
  id: 'daily-review' | 'distill-cards' | 'para-file' | 'connect-card' | 'wiki-compile';
  version: number;                       // 提示词或 schema 变化时递增，写入凭据
  allowedChanges: readonly ChangeKind[]; // 本任务能产生的写操作子集
  selectContext(input: TaskInput, index: KnowledgeIndex, budget: TokenBudget): ContextPlan;
  buildPrompt(plan: ContextPlan, locale: Locale): EnginePrompt;  // 含 JSON schema
  toProposal(output: Output, plan: ContextPlan): Proposal;        // 只做映射，不读写文件
}
```

## 5. 写操作白名单

写入执行器只认下表中的变更项，任务只能产生其 `allowedChanges` 里声明的类型。不在表中的操作（删除、移动、重命名、覆盖正文、修改 `.base` 文件和 `Records`、写入库外路径）在类型层面就无法表达。

| 变更项 | 作用 | 对应约定 |
| --- | --- | --- |
| `create-note` | 在指定目录新建笔记，带完整属性和正文；目标已存在则停止，不自动换名 | ZETTELKASTEN 7.2 固定路径与身份 |
| `append-section` | 在指定笔记的指定小节末尾追加内容（如 Journal 的「回顾」、卡片的「关联」）；小节不存在时在文末新建。目标笔记必须已存在；当日 Journal 不存在时，提案先列出一条按周期笔记设置新建 Journal 的 `create-note` | ZETTELKASTEN 5.5、6.4 |
| `add-connection` | 在卡片的「关联 / Connections」小节追加一条带关系和理由的链接 | ZETTELKASTEN 6.4 |
| `set-property` | 只设置 `tangrow_` 前缀的属性（如 `tangrow_sources`、`tangrow_project`）；合并列表时保留已有项和顺序 | ZETTELKASTEN 6.2 |
| `add-task` | 向配置好的任务目标追加一行任务，附来源链接 | DESIGN.md 任务写入规则 |
| `mark-processed` | 将速记标记为已处理 | ZETTELKASTEN 5.2 |
| `update-managed-block` | 替换主题百科页中托管区块的内容 | 本文第 8.5 节 |

所有变更项都要求：

- 记录目标文件和该项所依据的来源笔记在生成提案时的**修订摘要**。修订摘要由「规范化后的属性对象（忽略 YAML 排版与键顺序）+ 原始正文」共同计算（无属性区或属性区不可解析时回退为原文摘要），这样经宿主属性 API 重排 YAML 后仍可确定性比对。执行时任一修订不一致的，只暂停这一项，提示用户重新生成或手动处理，不覆盖。
- 同一变更集内对同一文件的多次写入（例如一张卡片上的多条 `add-connection`，或追加后再设置属性）按顺序串联核对：每一项以运行记录中该文件最后登记的修订作为预期修订，登记方式见第 7 节第 2 步。因此本变更集自己的写入不会被误判为冲突，只有变更集之外的修改才会让后续项暂停。
- 依赖新建笔记的变更项（目标是同一提案中 `create-note` 的路径，例如当日 Journal 不存在时先新建再追加回顾）：确认界面里勾选该项会同时勾选它依赖的新建项，取消新建项会同时取消依赖它的项；执行时新建项必须先成功，否则依赖项暂停。
- 目标文件在编辑器中打开且有未保存编辑时，走原生编辑器路径（ZETTELKASTEN 7.3），不用旧的 `vault.read()` 结果回写。
- 属性写入通过宿主属性 API。

## 6. 确认界面

确认界面是整理引擎的招牌体验，按以下原则设计：

1. **一屏看清规模**：顶部显示「将新建 3 篇、修改 2 篇」，以及本次运行的 token 用量。
2. **逐项可控**：每一项有勾选框、目标文件、变更类型、理由，以及依据的来源链接（可点开原文）。
3. **可先编辑再接受**：新建的卡片、回顾草稿可以在界面里直接改标题和正文。接受时固定的是编辑后的内容。
4. **差异预览**：`append-section` 和 `update-managed-block` 显示插入位置和前后差异。
5. **键盘优先**：`J/K` 移动，`Space` 勾选，`E` 编辑，`⌘Enter` 应用已勾选项，`Esc` 收起但保留提案。
6. **提案可以放着**：未处理的提案保存在运行记录中，今天页显示「待确认 N 条」。提案超过 7 天后整体标记为过期，只能重新生成。依据的文件修订变化时，只有涉及该文件的变更项标记为过期并暂停（第 5 节），其余项照常可应用。
7. 单次应用最多 8 个新建产物，与 ZETTELKASTEN 7.2 的批量上限一致；超出部分留在提案里分批应用。

## 7. 执行与恢复

沿用 ZETTELKASTEN 第 7 节的提炼凭据协议，不另起一套：

1. 用户点「应用」后，先把变更集写入运行记录：操作 ID、每个产物的 ID、路径、确认后的完整内容、`mark-processed` 固定的处理时间戳、各目标与所依据来源在生成提案时的修订摘要（作为每个文件的初始预期修订）、任务 ID 和任务版本。保存失败则不写任何文件。
2. 按「新建（`create-note`）→ 追加（`append-section`、`add-connection`、`add-task`）→ 托管区块（`update-managed-block`）→ 属性（`set-property`）→ 标记已处理（`mark-processed`）」的顺序逐项执行，每一项写入前先核对目标的预期修订。写入后的修订按写入方式登记：
   - **可预测写入**（新建笔记；文件没有未保存编辑时的追加、托管区块；经宿主属性 API 的属性写入，因为修订摘要按规范化属性计算，YAML 重排不影响结果，见第 5 节）：写入前按固定内容算出写入后内容的修订摘要，作为「预期写入后修订」登记进运行记录，再写文件。
   - **读回写入**（文件有未保存编辑、走原生编辑器路径时）：最终内容包含编辑器中尚未保存的用户编辑，无法预先算出。写入前只登记「本项写入中」，写入后立刻读取文件，登记实际修订。

   写入成功后登记该项已完成，并把登记的修订作为同一文件下一项的预期修订（第 5 节）。
3. 中断后从运行记录恢复：先读实际文件核对身份，再补齐未完成项。**恢复过程不调用模型、不重新读取源文生成内容**，只使用已固定的内容。写入与登记之间可能中断，所以每类写操作都能识别自己已经写入的结果：
   - `create-note`：按产物携带的操作 ID 和对象 ID 识别（ZETTELKASTEN 7.2）。
   - `append-section`、`add-connection`、`add-task`：追加内容带该变更项的稳定标记，沿用仓库既有的 HTML 注释格式（`<!-- tangrow:change:<id> -->`；来自速记的 `add-task` 沿用 `<!-- tangrow-capture:<id> -->` 或在 `report-source.ts` 兼容新标记，以保留速记结果覆盖率统计，且会被 `markdown-stats.ts` 剥离、不计入字数），按标记去重。落地 `add-connection` 时，`knowledge-index.ts` 的 `connectionAnnotation` 须先剥离行尾的 Tangrow HTML 注释，避免标记混入理由或破坏无理由连接的关系词解析。
   - `set-property`：标量属性值已等于目标值，或列表属性已包含本次合并写入的项（保留既有项与顺序，见第 5 节），即视为完成。
   - `mark-processed`：`tangrow_processed_at` 已等于凭据中固定的处理时间戳（或已存在有效处理时间）即视为完成。
   - `update-managed-block`：起始标记中记录的内容摘要已等于本次内容即视为完成。

   恢复时按目标文件的实际修订判断：
   - 等于预期写入后修订（仅可预测写入有此值）：本项已写入且之后没有别的修改，补登完成并照常推进修订链。
   - 等于写入前的预期修订：本项尚未写入，照常执行。
   - 两者都不是，但能识别出本项已写入（上面的标记或值）：可能是写入后文件又被修改过，也可能是读回写入在读回前中断，二者无法区分，一律保守处理。本项记为已完成、不重复写入，但同一文件的修订链在此中断，该文件的后续项按冲突暂停，由用户重新生成或手动处理。
   - 既不匹配、也识别不出本项：按冲突暂停。
4. 全部完成后清除凭据，并触发知识索引增量更新。

已确认的产物正文和属性作为临时快照保存在恢复凭据（引擎运行记录）中，全部完成后清除；这是恢复时不调用模型、不重读源文也能补建产物的前提，与 ZETTELKASTEN 7.2 一致。落盘后的产物笔记只带身份与来源属性：`tangrow_id`、`tangrow_sources`、`tangrow_derivation_id`，AI 起草的卡片另加 `tangrow_origin: ai`（见 8.2）。首批任务不新建稿件。

引擎变更集与源文件上已有的速记处理凭据（`tangrow_capture_processing`）或提炼凭据（`tangrow_derivation`）互斥：同一源文件有未结束的操作时，涉及该源的变更项暂停，先处理已有操作（ZETTELKASTEN 7.2）。

## 8. 首批任务

### 8.1 每日回顾（daily-review）

- **触发**：今天页「开始今日回顾」；可选在每天第一次打开 Obsidian 时预先准备提案（只生成，不写入；默认关闭，在首次使用引导里询问）。
- **输入**：当日和昨日的 Journal、当日新增速记和待处理速记、到期和逾期任务、当日卡片回顾队列（复用 `card-review.ts` 已持久化的队列，不另抽样；队列的优先级规则见 ZETTELKASTEN 8.2，包括 AI 起草卡片的优先）、近 7 日新建但未连接的卡片，以及 E3 落地后由本地内容摘要检出的待编入主题百科的新增或改动素材列表。
- **输出**：
  - 一段回顾草稿：今天记了什么、哪些想法值得展开、建议的三件事。确认后用 `append-section` 写入当日 Journal 的「回顾」小节。
  - 一组后续动作提案：例如「把速记 X 提炼为卡片」「把卡片 Y 连接到 Z」「把素材 W 编入主题百科」。每条动作都是一个可单独启动的任务运行，不在回顾里直接写入。
- **约束**：不把速记全文追加进 Journal（ZETTELKASTEN 5.1）；回顾草稿只引用链接和摘要。

### 8.2 卡片提炼（distill-cards）

- **触发**：速记 / 文献笔记 / 普通笔记上下文中的「提炼卡片」；选中文本右键；每日回顾的动作提案。
- **输入**：源笔记全文（或选段及其所在小节）；与之关键词相近的已有卡片标题和摘要（用于避免重复和建议连接）。
- **输出**：0–5 张候选卡片，每张包括标题（一个可独立理解的观点）、正文初稿、`tangrow_sources`、建议连接（指向已有卡片，附关系和理由）。可能和已有卡片重复的，提案里标为「可能重复」，并给出已有卡片的链接。
- **对卡片质量的约束**：CONTEXT.md 规定卡片是「用自己的话阐明」的观点。AI 写的只是初稿：
  - 新卡片带 `tangrow_origin: ai`，`tangrow_stage: seed`。
  - 卡片回顾队列优先抽取「AI 起草且未被用户修改过」的卡片，引导用户用自己的话改写。用户「标记已回顾」时询问是否已用自己的话改写，选「是」才清除 `tangrow_origin`；不根据文件修改时间推断。
  - 报表可以区分「AI 起草」和「已改写」的卡片数量。
- **源笔记状态**：提炼不改变速记的处理状态（ZETTELKASTEN 5.2）。速记提炼后仍待处理，用户可以在同一个确认界面里一并勾选 `mark-processed`。

### 8.3 PARA 归位（para-file）

- **触发**：收件箱 / 速记时间线的「整理收件箱」，可批量选择。
- **输入**：待处理速记及收件箱里的普通笔记；现有项目、领域、资源目录的列表和各自的简短描述（目录名 + 项目笔记标题 + `tangrow_project` 汇总）。
- **输出**：每条内容的建议去向，四选一：
  - 整理为笔记 → 指定的 Project / Area / Resource 目录；
  - 转为任务 → 配置的任务目标，可附项目；
  - 提炼卡片 → 转交 8.2；
  - 仅标记已处理。
- **约束**：
  - 目标目录可以是项目、领域或资源目录。速记处理区的手动表单另行约定：ZETTELKASTEN 5.2 的设计只用资源目录；当前实现建在所选项目笔记所在目录，未选项目时建在收件箱。
  - 已有笔记**不移动**。「整理为笔记」是新建一篇普通笔记并链接原速记（ZETTELKASTEN 5.2）；收件箱里的普通笔记只建议设置 `tangrow_project`，不搬文件。
  - 建议的目录和项目必须是现有的；指向不存在的项目时丢弃该建议，与现有即时建议的规则一致。

### 8.4 卡片连接（connect-card）

- **触发**：卡片上下文面板的「找连接」；回顾队列中「待连接」的卡片。
- **输入**：目标卡片全文；按链接邻近、共同来源、标题和关键词相近程度选出的候选卡片（每张只取标题和前几段）；候选结构笔记，即已收录这些候选卡片或与目标卡片链接相邻的结构笔记（只取标题和小节标题）。加入结构笔记的建议只能指向这些已在上下文中的结构笔记。
- **输出**：最多 5 条连接建议，每条包括目标、关系（支撑 / 反驳 / 延伸 / 举例 / 对比 / 相关）和一句理由。也可以建议把它加入某个已有的结构笔记。
- **写入**：`add-connection` 只修改发起连接的卡片；加入结构笔记用 `append-section`，只修改用户勾选的那篇结构笔记（ZETTELKASTEN 6.1）。

### 8.5 主题百科编译（wiki-compile）

主题百科（对外也称 llm-wiki）指：由模型从素材中持续编译、互相链接的主题页面集合。它回答「关于某个主题，我收集的材料说了什么」。结构笔记（Hub）回答「我怎么组织自己的论证」。两者用途不同，因此新增 `tangrow_kind: wiki`（主题百科），不复用 `hub`。

- **触发**：今天页的「N 篇素材待编入主题百科」入口（独立于第 6 节的「待确认 N 条」提案列表，只按本地内容摘要检测新增或改动的素材并计数，不调用模型）；命令「编译主题百科」；每日回顾中的动作提案。三种入口都由用户点击后启动同一个任务运行，照常经过发送预览（第 9 节）和确认界面。
- **位置**：资源目录下一个可配置的子目录，默认 `<资源目录>/Wiki`。
- **不是素材**：`wiki` 加入素材排除列表（`card-report-data.ts` 的 `NON_MATERIAL_KINDS`），知识区素材列表、卡片报表和稿件候选的默认素材都不包含主题百科页；`wiki-compile` 的输入也排除 `tangrow_kind: wiki` 和主题百科目录，避免编译结果回流成新素材。报表的资源条目统计同样排除主题百科页，口径并入 REPORTING.md 时注明。
- **页面结构**：
  ```markdown
  ---
  tangrow_kind: wiki
  tangrow_id: …
  created: "…"
  tangrow_sources:
    - "[[素材 A]]"
    - "[[素材 B]]"
  ---
  # 主题名
  <!-- tangrow:wiki:start rev=… -->
  （由 Tangrow 维护的摘要、要点、分歧、相关主题链接，每条结论标注来源）
  <!-- tangrow:wiki:end -->
  ## 我的笔记
  （用户自由编辑，Tangrow 从不改动）
  ```
- **增量编译**：
  1. 运行记录保存每个素材的内容摘要，以及它被编入了哪些主题页。
  2. 新增或改动的素材先做「主题归类」，产出提案：把它编入哪些已有主题页，或新建哪个主题页。
  3. 用户确认后，对受影响的主题页逐页重新生成托管区块（`update-managed-block`）。
- **用户编辑保护**：托管区块的起始标记里记录上次写入内容的摘要。用户手动改过区块的，暂停该页的更新，并给出新旧差异由用户选择，不静默覆盖。
- **规模控制**：每次运行最多处理 10 个素材、更新 5 个主题页；其余排队，可暂停，显示累计 token 用量。

## 9. 上下文与隐私

1. **发送前预览**：每次运行前展示将发送的笔记列表、估算 token 数和目标服务商。可以勾掉不想发送的笔记。可在设置中选择「信任的任务直接运行」，但首次运行每个任务时必须展示一次预览。
2. **排除规则**：默认排除辅助目录、归档目录、`reportExcludedFolders`；另外支持笔记属性 `tangrow_ai: false` 和设置里的排除目录列表。被排除的笔记即使被链接到，也只发送标题。
3. **不静默截断**：沿用现有规则，超出预算时按任务定义的优先级裁剪，并在预览里列出被裁掉的内容；仍放不下就报错，要求缩小范围。
4. **提示注入**：笔记正文一律放在明确标记的数据区，系统提示声明其中的指令无效。写操作受白名单约束、每次写入都要确认，所以即使模型被诱导，也只能产生用户看得见、可拒绝的提案。结果校验会丢弃指向上下文以外路径、或新建路径越出任务允许目录的变更项（与第 4 节「结果校验」一致）。
5. **密钥**：继续优先使用宿主密钥存储。现有 `AI_SECRET_ID` 只对应 Anthropic 密钥；新增服务商各自使用独立的密钥 ID，不复用这一常量。

## 10. 模型适配层

```ts
interface Provider {
  id: 'anthropic' | 'openai-compatible';
  generate(req: {
    system: string; messages: EngineMessage[]; schema: JsonSchema;
    maxTokens: number; signal: AbortSignal; onProgress?(chars: number): void;
  }): Promise<{ json: unknown; usage: { input: number; output: number } }>;
}
```

- **Anthropic**：沿用 `src/ai-client.ts` 中的官方 SDK 和流式调用；结构化输出用 JSON schema。
- **OpenAI 兼容接口**：通过 Obsidian 的 `requestUrl` 调用，以避开移动端的跨域限制。`requestUrl` 不支持流式输出，对结构化任务可以接受，界面只显示「生成中」。它也不接受 `AbortSignal`：取消只是逻辑取消，即请求照常完成，但结果被丢弃，不进入提案，用量仍计入。
- **移动端**：需要实测 Anthropic SDK 在 iOS / Android 上的 `fetch` 行为；不可用时，Anthropic 也改走 `requestUrl`。
- **模型选择**：设置中用下拉选择预设模型，「自定义模型 ID」放进高级选项。每个任务可以指定使用「快速」或「强」两档之一（例如归类用快速档，卡片初稿用强档），默认值由任务定义给出。
- **失败处理**：网络错误自动重试 1 次；输出不符合 schema 时，带上校验错误重试 1 次，仍失败就显示原始输出，不写入任何内容。

## 11. 与现有功能的关系

| 现有能力 | 处理方式 |
| --- | --- |
| 即时建议（快速新建 / 速记处理预填） | 保留；底层改用模型适配层，以便共享服务商设置和密钥 |
| Claudian 工作流：整理收件箱 | 由 8.3 PARA 归位取代 |
| Claudian 工作流：写周回顾 | 在每日回顾稳定后，扩展出周期回顾任务（周 / 月）来取代 |
| Claudian 工作流：关联笔记 | 卡片由 8.4 卡片连接取代；非卡片笔记暂无引擎替代，因此该工作流在侧栏保留到引擎提供普通笔记的关联任务为止 |
| Claudian 工作流：检查未完成任务、项目简报、拆解项目 | 暂留 Claudian；后续视需要迁移为只读或 `add-task` 任务 |
| 库级技能导出 | 保留，作为高级用户在 Claude Code / Claudian 中使用的入口 |
| AI 页签 | 整理动作嵌入各自的上下文（速记、卡片、今天页）。AI 页签收缩为「运行记录与待确认提案」以及 Claudian 入口 |

迁移期间，同一能力只保留一个主入口：某个任务完整覆盖原工作流后，对应的 Claudian 工作流才从侧栏移除，只在技能导出里保留。

## 12. 授权与计费

- 整理引擎属于付费功能范围，遵循 [授权核心约定](ACCESS-CONTRACT.md) 和 [购买激活](PURCHASE-ACTIVATION.md)。以 `plugin.access.canUse()` 为准，与插件其他功能使用同一门禁。返回 `false` 时（无论状态是 `expired`、`not_started` 还是 `needs_network`）不能发起新的运行，也不能应用提案。**已经开始执行的变更集无论授权状态都允许完成或恢复**，避免留下半写入状态。
- 模型费用由用户的密钥承担。界面显示每次运行和当月累计的 token 用量（本地统计，不上报）。
- 落地 E0（门禁接入）和 E4（移动端、多服务商）时，同步更新 PURCHASE-ACTIVATION.md：付费功能范围、多服务商自带密钥（BYOK）的说明，以及「始终放行边界与草稿保护」中的「在途操作收尾」——把已开始执行的引擎变更集的完成与恢复列入始终放行的在途操作。

## 13. 已定决策

以下问题已于 2026-11-26 确定，并已同步到 [统一设计方案](ZETTELKASTEN.md)（3.1、3.3、5.2、6.2、7.2、8.2）和 [领域语言](../CONTEXT.md)。

1. **可以直接从速记提炼卡片。** 引擎的卡片提炼接受速记作为来源，不要求先整理为普通笔记；来源关系照样写入 `tangrow_sources`，速记的处理状态不变。ZETTELKASTEN 5.2 和 7.2 已注明这一例外。
2. **PARA 归位可以指向项目、领域和资源目录。** 仍然只新建笔记、不移动已有文件。速记处理区的手动「整理为笔记」表单不受此决策影响（按 ZETTELKASTEN 5.2 的设计只用资源目录；当前实现见 8.3）。
3. **llm-wiki 使用新类型 `tangrow_kind: wiki`**，在 CONTEXT.md 中称为「主题百科（Wiki）」，与结构笔记（Hub）区分。
4. **`tangrow_origin: ai` 在用户「标记已回顾」时清除**：标记时询问是否已用自己的话改写，选「是」才清除；选「否」则保留标记，卡片下次仍优先进入回顾。
5. **每日回顾的预先准备默认关闭**，在首次使用引导里询问是否开启。

## 14. 测试与验收

**确定性测试**（`npm test`）
- 每个任务的 `toProposal`：给定模型输出 → 预期的变更项；越权路径、不存在的项目、未知关系类型都被丢弃。
- 白名单：任务声明之外的变更类型被拒绝；`set-property` 拒绝非 `tangrow_` 键。
- 修订核对：目标文件或所依据来源的修订变化后，对应项暂停，其他项继续；同一文件的多项写入按登记的修订串联通过，经宿主属性 API 重排 YAML 后不误报冲突；依赖新建笔记的项在新建项未被接受或未成功时不执行。
- 恢复：在每个执行阶段注入失败，包括「文件已写入、尚未登记」的中断点（覆盖 `create-note`、追加标记、`update-managed-block`、`set-property` 列表合并与 `mark-processed`），该中断后用户又修改同一文件的情况（后续项必须暂停），以及读回写入在读回前中断的情况；正常执行时，宿主属性 API 重排 YAML、或经编辑器路径写入，都不得导致后续项误报冲突；恢复后的结果与一次成功执行相同，没有重复写入、没有误报冲突，且没有调用模型；带 HTML 注释标记的 `add-connection` 仍能正确解析关系词与理由。
- 托管区块：区块外内容逐字节不变；用户改过区块后暂停更新。
- 上下文预算：超出预算时按优先级裁剪并在预览中列出，放不下则报错。

**真实宿主验收**
- 在桌面端和至少一台移动设备上完成「速记 → 提炼卡片 → 确认 → 次日出现在回顾中」。
- 确认界面在浅色 / 深色、窄侧栏下可用；中文输入法下编辑候选卡片不丢字（按 [输入法验收](NATIVE-IME-ACCEPTANCE.md)）。
- 断网、密钥无效、限流、模型返回非法 JSON 时，均不写入任何内容，并给出可操作的提示。
